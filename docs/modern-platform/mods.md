# Resource Mods, first version

Mod work lives in `C:\WorkSpace\6kinoko-mods` on branch `codex/mod-overlays`.
This is an isolated game checkout, not a second engine or an editor UI.
The TAS thread owns replay/control/rendering; this batch changes resource reads.

## Windows usage

Use the delivered `Launch-Cursor-Mod.cmd` to enable the example, then ordinary
`launch.cmd` to play without it. Python 3.10+ is needed by the Mod launcher;
ordinary game execution does not require Python. No game DAT is redistributed.
The original three DAT files remain beside the game executable and unchanged.

The example replaces `data/system/title/title_cursor.cv2` with an original cyan
arrow, 64x32 BGRA, and carries no extracted proprietary pixels. Inspect the title
menu to see it. Binary image was generated by the included standard-library script.

General command (repeat --mod in low-to-high priority order):

```powershell
python mod_session.py --game .\kinoko_modern_gpu.exe --mod .\mods\cyan-title-cursor
```

Add `--prepare-only` to validate/build the session without running the game.
Default conflicts are errors. `--allow-overrides` explicitly enables later-wins;
all winners and overridden paths are listed in `session.json`. Dependencies
require exact id/version and must be enabled earlier. No automatic reordering.

## Manifest

```json
{
  "format": 1,
  "id": "cyan-title-cursor",
  "name": "Cyan title cursor",
  "version": "1.0.0",
  "requires": [],
  "files": ["data/system/title/title_cursor.cv2"]
}
```

Listed files are relative to mod.json. Initial path schema permits ASCII data/...
resource paths, case-insensitive and slash-normalized on lookup. Duplicate case
variants, traversal, absolute paths and escaping links are rejected. Files are
limited to 64 MiB. Non-ASCII resource names and dependency version ranges are
future extensions. Additional resource files can be supplied, but no game script
or level registration is generated for them automatically.

Only the game's unified archive-resource reader is overlaid. Save files, native
libraries, fonts/shaders beside the executable and loose platform files are not
covered. Archive formats and original lookup behavior remain intact on misses.
Matched-but-unreadable/changed overrides fail rather than silently returning DAT.

## Snapshot, identity and saves

The launcher parses mod.json using Python's standard JSON parser, computes SHA256,
then copies only effective replacement files into a fresh `mod-sessions/<id>-.../`.
`catalog.tsv` contains ordered Mod id/version/content hashes and sorted effective
resource paths/hashes. Its SHA256 is the session's Mod identity, independent of
absolute paths and filesystem enumeration order. Metadata and dependency changes
that affect identity are explicit; display name is not simulation identity.

Native startup verifies every snapshot resource. Each overridden resource is
hash-checked again when opened; edits require a new session. Startup is transactional:
invalid catalog/hash disables the entire set and reports an error before scripts.
Catalog is a prepared internal format, not the user-facing authoring format.
This is integrity checking, not a sandbox for untrusted game scripts.

Mod saves live under `mod-saves/<full-identity>/`; original progress is not copied.
On first use, only keyconfig.dat/input-actions.cfg are copied for controls. Same
Mod combination/content reuses progress; changing content/order selects another
save directory. All snapshots/logs are retained. No automatic deletion or hot reload.

`mods::active()` exposes the ordered `Info{id,version,content_sha256}` list;
`mods::identity()` returns the full catalog SHA256, empty when disabled.
The startup hook is immediately before replay initialization. No runtime option
parser or replay implementation is modified. Until this identity is integrated
into recording/TAS session identity, enabled Mods plus replay/record are rejected.
This is a temporary explicit boundary, not a claim of Mod replay support.

## Checks and scope

Native checks cover SHA256 vectors, content validation, mutation rejection and
resource resolution. The existing archive fixture proves overlay bytes win over
DAT and disabling restores DAT bytes. Python checks cover dependencies, conflict
policy, deterministic identity, changed content, save isolation and retained snapshots.
No agent gameplay testing. Mod-manager UI, map preview/editing, new enemies/Bosses
and role transformations are later stages built on this resource layer.

## Distributable packages and installed profiles

A `.kmod` is a deterministic ZIP containing normalized mod.json, exactly the
listed data/... files and checksums.json. It supports both overrides and entirely
new resource paths. The game reader does not require an original DAT entry.
Game scripts/registries must still reference new assets to use them; installing
an image does not automatically register a new enemy or level.

Windows: drag a `.kmod` onto `Install-Mod.cmd` to install and enable it, then use
`Launch-Mods.cmd`. Installation and activation are distinct: a dependency/conflict
error leaves the validated package installed but does not change the active profile.
Ordinary `launch.cmd` still runs without the managed Mod profile.

```powershell
python mod_manager.py pack mods/cyan-title-cursor cyan-title-cursor.kmod
python mod_manager.py install --game kinoko_modern_gpu.exe cyan-title-cursor.kmod
python mod_manager.py list --game kinoko_modern_gpu.exe
python mod_manager.py enable --game kinoko_modern_gpu.exe cyan-title-cursor
python mod_manager.py launch --game kinoko_modern_gpu.exe
python mod_manager.py disable --game kinoko_modern_gpu.exe cyan-title-cursor
```

`enable` accepts --version / --hash when multiple revisions are installed. Updates
keep all previous revisions under installed-mods/id/version/content-sha256. It does
not choose an arbitrary newest version. `move --game ... ID POSITION` changes the
zero-based low-to-high load order, validating dependencies before saving. Enable
with --allow-overrides explicitly permits resource conflicts for this profile.
`launch --prepare-only` resolves the profile and snapshots without executing game.
An empty profile launches the ordinary game with ordinary saves.

mod-profile.json stores exact identities/order; history/ retains previous profile
files before atomic replacement. Invalid edits leave the previous profile active.
There is no uninstall/cleanup operation in this version. Failed or duplicate
installation staging directories are retained but excluded from installed discovery.

Package install checks paths, duplicated names, symbolic links, encryption, exact
manifest/inventory and SHA256. Limits: 64 MiB/resource, 1 MiB/metadata, 512 MiB total,
10002 ZIP entries. No extractall is used. Checksums verify integrity, not publisher
identity or script trust. Package compilation does not bundle DAT or other unlisted
files. Mod management currently uses launch scripts/CLI; a graphical manager is
not included yet.
